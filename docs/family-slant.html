Family slant review

After the per-file handlers finish, FontFixer can compare measured italic angles within each family and recommend italic/oblique flag fixes when siblings disagree with the upright vs slanted picture. Angles are never rewritten here.

No new CLI flag. The review runs automatically after a normal interactive run that included the style handler. It is skipped for -n, --validate-only, non-TTY sessions, or when style was not run.

When it runs

  1. Main pass completes (os2 → style → glyph → kern as selected).
  2. Session is an interactive TTY (not piped / CI).
  3. style was among the handlers that ran.
  4. Survey prints for every family in the run; only actionable families reach the prompt.

How families group

Members are grouped by typographic family name:

  • nameID 16 preferred (typographic family)
  • else nameID 1 (legacy font family)
  • else a filename stem with trailing weight/width/slope tokens peeled off

Preferring ID 16 matters for RIBBI-split naming: weights like Black/Book/Light often put the weight in ID 1 (Babel Black) while ID 16 stays Babel. Using ID 1 first would treat each weight as its own one-cut family and skip them all as incomplete.

Style pass vs family review

Style handler (per file)Family slant review
Angles / caret / CFF Measurement-driven (multi-glyph median; named italics keep a non-zero angle if measurement is weak) Not rewritten
Italic / oblique bits Name labels only — measured slant does not mark a Roman as italic May recommend SET/CLEAR when siblings show a clear upright vs slanted split
Prompt None Apply all / Review each / Quit

Survey labels

Each family gets one status row (FontCore semantic labels):

  • OK — flags already match the family’s upright/slanted picture
  • WARNING — actionable: recommend SET and/or CLEAR italic (or oblique) bits
  • SKIPPED — no safe recommendation (see reasons below)

When a family is skipped

ReasonMeaning
incomplete family (only one cut) Single member in this run — no sibling comparison
no upright reference Every cut looks slanted by angle (often upright designs with noisy italicAngle)
no slanted cuts All members look upright — nothing to compare
ambiguous spread Upright vs slanted peaks differ by less than 2°
roman-only family No named Italic/Oblique cuts — angle spread alone is not enough to SET italic (weight-correlated roman noise). Misplaced italic bits on the upright side can still be CLEARed

Recommendation rules

  • Cluster members into upright vs slanted using measured angle (2° floor) and sibling context.
  • If the family already has named Italic/Oblique cuts, unlabeled Romans stay on the upright side — mild positive angles on Regular/Bold do not invent a third slant band.
  • Recommend CLEAR italic/oblique bits on the upright cluster when they are set.
  • Recommend SET italic (or oblique, when named) on the slanted cluster when bits are missing — only when the family has named Italic/Oblique anchors, or when clearing upright mismatches. Pure roman families do not get SET from angle alone.
  • Forward (negative) and backward (positive) slanted cuts both count as slanted; multi-band families keep flags on all slanted sides.

Prompt

1. Apply all recommended flag fixes
2. Review each recommended family
3. Quit (leave flags unchanged)

Quit (or choosing skip while reviewing) leaves flags as the style pass left them. Nothing is applied silently.

Still interactive. Uncommon naming can be intentional. Prefer Quit or Review each when the survey looks surprising; use -o on the main pass if you want tidied copies before accepting flag changes.
